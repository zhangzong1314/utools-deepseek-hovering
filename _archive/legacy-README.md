# DeepSeek 悬浮助手（uTools 插件）

在 Windows 桌面上放一个置顶的蓝色悬浮球，单击即可打开 `https://chat.deepseek.com/` 对话。
登录直接用 DeepSeek 官网账号（手机号 / 邮箱 / 微信），本插件不建自己的账号体系、不碰对话内容。
对话窗按手机比例开着（默认 460×900，比真机大一圈），关掉前在哪个会话，下次开窗直接回到那个会话。

## 目录结构

```
plugin/            ← 插件根目录：uTools 加载/打包的都是这个目录
  plugin.json        插件元信息与功能声明（入口）
  preload.js         主 preload：生命周期、窗口管理、与主面板的桥
  index.html         主面板（在 uTools 搜索框里显示）
  js/config.js       配置读写（dbStorage）
  js/windows.js      悬浮球窗与对话窗的创建/复用/拖拽/菜单几何/尺寸与会话地址策略
  js/repair.js       兜底：在 Node 侧取回官网脚本、按 integrity 验过哈希再灌进对话窗（Node 内置模块，无外部依赖）
  js/trace.js        排查日志：把"这个窗口里失败的请求"追加写到临时目录下的一个文件里（不碰请求体，只记地址与方法）
  page/ball.html     悬浮球页面（含右键菜单与拖拽逻辑）
  page/ball-preload.js  悬浮球窗的 preload（IPC 桥）
  page/chat.html     对话窗落地页：自己跳转到官网，跳不动时显示兜底界面
  page/chat-preload.js  对话窗的 preload：告诉页面该跳哪、把当前地址报回来、认出官网的资源校验失败页并生成诊断报告
  page/panel.js      主面板交互
  assets/logo.png    插件图标（由 tools/gen-icons.js 依据 whale.svg 生成）
  assets/whale.svg   官网图标（favicon 的鲸鱼路径）：悬浮球、面板、图标生成器共用这一份
tools/             ← 开发自检用，不进插件包
package.json, README.md, .gitignore
```

**`plugin.json` 为什么放在子目录里**：uTools 是拿 `plugin.json` 所在的目录当插件根来加载和
打包的，整个目录会被一起读进去。要是把它放项目根目录，`tools/`、`package.json`
这些工程文件就会跟着进插件包。所以运行时文件全部收在 `plugin/` 下，脚手架留在外面。

## 在 uTools 里调试

1. 打开 uTools → 右上角头像 → **开发者工具** → 新建/加载项目。
2. 项目路径选到本仓库的 **`plugin`** 目录（不是仓库根目录，理由同上）。
3. 保存后回到 uTools 主搜索框，输入 `deepseek`（或 `ds`、`深度求索`、`ai对话`、`悬浮球`）回车。
4. 出现主面板，桌面上同时出现悬浮球。

## 用法

| 操作 | 结果 |
| --- | --- |
| 单击悬浮球 | 对话窗开着就关掉，没开就打开（在面板里也可以改成"在浏览器中打开"） |
| 按住悬浮球拖动 | 移动位置，松手后位置会记住，重启 uTools 仍在原处 |
| 右键悬浮球 | 弹出菜单：打开/关闭对话 · 在浏览器中打开 · 隐藏悬浮球 |
| 主面板「显示/隐藏悬浮球」 | 开关悬浮球 |
| 主面板「打开对话 / 关闭对话」 | 直接开关内置对话窗（按钮文案跟着窗口状态变） |
| 主面板「悬浮球不见了」 | 清掉记住的位置，把球放回主屏右下角 |
| 全局快捷键（需自己绑键） | 把对话窗**叫到跟前**：没开就打开，被盖住就调到最前，已经在最前面再按一下才关掉 |

### 面板设置

- **单击悬浮球时**：在内置独立窗口打开（推荐，登录态与浏览器互不影响）／在系统默认浏览器打开。
  这一项只管"单击悬浮球"这一个动作；面板上那颗「打开对话 / 关闭对话」按钮永远管内置窗口。
- **对话窗大小**：填宽和高（像素）后点「应用」或按回车。默认 `460 × 900`（手机比例），
  范围是 `320 × 400` 起，再大也不会超出当前屏幕的可用区域 —— 填进来的值会先被夹进合法区间
  再存，面板回填的就是下次真正会用的大小。改动在**下次开窗**时生效。
- **恢复默认**：清掉存过的尺寸，回到 `460 × 900`（手机比例）。
- **全局快捷键**：只读地显示"现在绑的是哪个键"，点「设置」跳到 uTools 的快捷键设置页去绑。
  插件**没法自己抓按键组合**（原因见下面「快捷键」一节），所以这里不提供输入框。

### 快捷键

**先绑键**：uTools 设置 → 全局快捷键 → 找到本插件的指令「**DeepSeek窗口**」→ 绑一个键
（面板上点「设置」会直接跳到那一页）。绑好回到面板，那一栏就会显示出你配的键。

**按下之后干什么 —— 和点悬浮球是两套语义**：

| 按下快捷键时对话窗的状态 | 结果 |
| --- | --- |
| 没开 | 打开，并且直接在最前面 |
| 开着，但被别的窗口盖住（或已最小化） | 调到最前面（最小化的先还原），**不关** |
| 开着，而且就在最前面（标题栏是激活的） | 关掉 |

点悬浮球则是**纯开关**：开着就关。两者的差别都在同一格上 —— 窗口开着但不在眼前时，
点球关掉它容易误伤（你可能只是想把它叫出来），快捷键负责"叫到跟前"，所以那一下不关。
真想把"看得见的窗口"收掉，两种方式都行：两种情况下，窗口就在眼前时再按一下／再点一下都是关掉。

另外两点：

- 不管「单击悬浮球时」选的是内置窗口还是系统浏览器，**快捷键永远管内置对话窗**：
  浏览器窗口没法被"调到最前"，更没法判断它是不是已经开着，三态语义根本立不住。
- uTools 主搜索框里敲 `DeepSeek窗口` 回车是同一条路：效果一样，只是搜索框会顺手让开。

### 记住上次的会话

对话窗会在每次导航后把当前地址报给父窗，策略集中在 `js/windows.js` 的 `rememberChatUrl()`：

| 报上来的地址 | 处理 |
| --- | --- |
| `https://chat.deepseek.com/a/chat/s/<id>` | 记住（hash 剥掉，查询串保留） |
| `https://chat.deepseek.com/`（对话首页） | 忘掉，下次从首页进 |
| 登录页、跳转页、站外地址 | 不碰，保留已记住的会话 |

下次开窗时 `page/chat.html` 会直接跳到记住的那个会话；没有记录就是官网首页，
DeepSeek 自己会落到新对话。这个默认行为是**刻意的**：回到首页意味着忘掉上次的会话，
而不是把它冲成一条更烂的记录。

会话地址存在 uTools 的 dbStorage 里，和上面那条登录态不一样 —— 它是**真的落盘**的
（`%APPDATA%\uTools\database\<插件id>\` 下能直接搜到那两条会话地址），重启 uTools 也还在。
所以"重启要重新登录"和"重启还能回到上次的会话"这两件事并不矛盾：前者是浏览器的会话，
后者是插件自己的配置。

## 打包

用 uTools 开发者工具自带的打包功能，打包对象选 **`plugin`** 目录（不是仓库根目录），
产物是根目录含 `plugin.json` 的 `.upx`。本项目不带打包脚本。

**打包器会自己重写 `plugin.json`，而且换掉插件 id。** 装好之后 uTools 把插件放在
`%APPDATA%\uTools\plugins\unsafe-<md5>.asar`，里面的 `plugin.json` 是**打包器生成的压缩单行版**：
`pluginName` / `author` / `description` 取自打包表单（不填就默认取目录名之类，比如本插件会变成
`deepseek-hovering`），另外补上 `platform`、`name`（插件 id，如 `zup4nqkv`）这些字段；
`features` 数组原样保留，所以 `cmds`、`mainHide` 都在。

要紧的是这个 id：dbStorage 的目录名就是它（`%APPDATA%\uTools\database\<插件id>\`），
**开发时的 id 和安装后的 id 不是同一个**。也就是说悬浮球位置、窗口大小、记住的会话地址
这些配置在"开发者工具加载"和"装包运行"之间**不会互相带过去**，两边各存一份；
对话窗的登录态同理（本来就不落盘，见上面「登录态不落盘」）。验收打包版本时，
记得在安装版里重新登录、重新设一次。

## 开发时能跑的自检

```bash
npm run check     # 校验 manifest、语法、资源引用，并用桩件跑一遍完整链路
npm run icons     # 照着 assets/whale.svg 重新生成 assets/logo.png
```

`check.js` 会用桩件把 preload.js 真正跑起来，模拟「进入插件 → 建悬浮球 → 点球开关对话 →
拖球 → 右键菜单 → 改设置 → 隐藏球」整条链路，断言窗口创建参数和状态流转；
`createBrowserWindow` 的回调按"加载完成后触发"和"创建时同步触发"两种时序各跑一遍。
GUI 里点不出来的低级错误基本都能在这里拦住。

`check.js` 还会核对 `assets/logo.png` 是不是照着当前的 `assets/whale.svg` 生成的：
`gen-icons.js` 会把源路径的 sha256 前 16 位写进 PNG 的 `tEXt` 块里，改过 `whale.svg`
却忘了重跑 `npm run icons` 的话，这里会直接报出来（否则表现只是"图标没变"，很难联想到原因）。

## 已知限制

**对话窗里出现「页面资源加载异常，请刷新重试」—— 这句话不是插件说的，是 DeepSeek 官网自己的错误页。**

官网的两个 `<script>` 带 `integrity`（SRI 完整性校验）。**任何一只脚本没加载成**
（校验没过、或者请求压根没发出去），都会触发他们内联的 `onerror`，把 `document.body`
整个换成一张图（容器 class 是 `_sri-ck`，按钮写死 `onclick="location.reload()"`）。
所以这不是"插件页面加载失败"，而是**官网没能执行它自己的 JS**。
函数名叫 `_sriCk` 只是因为作者预判最常见的病因是 SRI —— **那张图本身不说是哪种**，
详见下面「一句话自我纠正」那一段。

浏览器拒掉一只脚本有两条路：**字节和 HTML 里写的哈希对不上**（SRI 校验失败），
或者这次请求根本没走成（跨域脚本带 `crossorigin`，要先过一次 CORS 校验）。
两条路的表现一模一样 —— 都是官网弹那张图。判断起来也很直白：

| 现象 | 结论与处理 |
| --- | --- |
| 同一台机器用系统浏览器打开 `chat.deepseek.com` 也这样 | 网络链路上有人改了响应：代理 / 加速器 / 公司中间缓存。关掉代理，或让 `*.deepseek.com`、`fe-static.deepseek.com` 走直连 |
| 只有 uTools 的对话窗这样，浏览器正常 | 要么是本地缓存里躺着一份坏副本（官网的 JS `max-age` 是 30 天）——**完全退出 uTools**，删掉 `%APPDATA%\uTools\Cache` 和 `Code Cache`（都只是 HTTP 缓存，删了只会让下次加载慢一点），重启再试；要么就是下面那条 CORS 路 |


插件自己会救一次：`page/chat-preload.js` 认出这张图（`._sri-ck`）后通知父窗
**绕过缓存重载**（`webContents.reloadIgnoringCache`，拿不到就退回普通 reload）；只救一次 ——
标记写在 sessionStorage，第二次就把页面交还给官网自己的「重新加载」按钮，
免得网络真坏了的时候陷入自动刷新循环。

**救不回来时，它会把"现场侦察"直接摆在窗口里。** 两种情况会生成这份报告：第二次认出这张图
（说明那次绕过缓存的重载也没用），或者重载压根没能发生 —— 请求发出去 5 秒后页面居然还活着。
生成报告时会挨个重新取一遍官网那两个带 `integrity` 的脚本，**每个取两遍**：
`fetch(src, { cache: 'no-store' })` 拿到"此刻网络上那份"，再默认缓存模式取一遍拿到
"浏览器刚才真的用的那份"，各自算 SHA-384 和 HTML 里写的那串比。
这是唯一能把几种情况分开的办法，浏览器对 SRI 失败不给原因：

| 侦察结果 | 含义 |
| --- | --- |
| **绕过缓存那份对、走缓存那份不对** | 缓存里躺着坏副本 —— 浏览器用的正是那份。清缓存（见上表），或点「重新加载（绕过缓存）」 |
| 两遍都**对得上**，且 `Content-Type` 是 javascript | 网络是干净的：字节没问题，是这次脚本加载在别处被卡住了（见下面「实测结论」）。报告里的 `Access-Control-Allow-Origin` 一般是读不到的（那个头不在 JS 可见的白名单里），别拿它当证据 |
| 两遍都**对不上** | 网络链路上有人一直在换内容 —— 代理 / 加速器 / 中间缓存给了坏副本 |
| 拿回来的 `Content-Type` 是 html | 网关/WAF 插了一张错误页当脚本发下来了（报告里会带上它的开头几十个字节） |
| 两遍都**取不到** | 请求在 CORS 或网络这一层就被拒了（同样是代理、网关这一类） |

报告里还有一行 **`这次加载`**，取自 `performance.getEntriesByType('resource')`：那是**浏览器自己记的
那次失败的加载**拿到了什么。它和上面几行是两码事 —— 上面几行是事后重取，事后重取永远正常，
所以只能回答"网络此刻好不好"，回答不了"当时那次到底怎么了"。这一行才分得开：

- 状态码 **429 / 403**、字节数很小 → 被限流或拦了（瞬时问题，隔一会儿就好）
- **一个字节都没拿到** → 请求根本没成。注意这跟"连不上"不是一回事：见下面那条实测结论
- 状态码 **200** 且字节数和网络上那份一样 → 内容拿到了却被拒，那就是校验/CORS 这一层的事

另外两行是这一轮新加的：**`界面 : #root 有 N 个子节点`**（脚本没跑起来时这里会是 0）、
**`拦截 : 指令 ← 被拦的地址`**（页面若被施加了 CSP，拦下来的东西在这儿留痕；本机实测官网
没有资源级 CSP，这行不出现）。脚本后面还有一段 **`── 样式表`**，每只样式表一行、同样报
"这次加载"拿到了什么，拿不到字节的会标 `← 需要重取`（放行那一步要连它一起补）。

最后一段是 **`── 这个窗口里失败的请求`**，而且它是**每次点「复制」时现算的**，不是生成报告
那一刻的快照 —— 这一点是刻意的：放行只解决"界面起不来"，真正会出故障的是放行**之后**那一段
（登录、拉会话、发消息）。所以 `page/chat-preload.js` 在页面最早期（preload 比官网脚本先跑）
就把 `XMLHttpRequest` 和 `fetch` 各包了一层，**只观察不改写** —— 原函数照常调用、返回值原样返回、
异常照旧抛出去，不加 WebSocket / EventSource（包构造函数的代价比这点收益大，而登录这一步
走的一定是 XHR 或 fetch）。手机号验证码这一步若失败，这一段就是唯一的线索：

| 记到的东西 | 含义 |
| --- | --- |
| **`→ 失败（连接层面没成）`**（status 0） | 和那两只脚本同一个病：请求在发出去之前就被挡了。网络是好的（同一时刻页面自己发 `fetch` 拿得到 200） |
| `→ 超时` | 请求发出去了，没人回 —— 这才是真的网络/WAF 那一侧 |
| `→ HTTP 4xx / 5xx` | 请求走通了，是 DeepSeek 服务端不受理（风控、限流、参数不对），**与这个窗口无关** |

这三行是分得开的，而"官网只回一句网络异常"分不开 —— 这就是要自己记的原因。

字段来源：`responseStatus` / `decodedBodySize` / `transferSize` / `duration`。官网这台 CDN 回了
`timing-allow-origin: *`，所以这些数字对我们可见（没有它的话跨域资源的这些字段会被浏览器抹成 0）。

**实测结论（2026-10-14，装好的插件里跑出来的）：那两只脚本的 `这次加载` 都是 `HTTP 0、0 字节、1~2ms`
—— 请求根本没发出去就被挡了。** 这件事的全部意义在于它排除了一整类解释：
网络、代理、缓存、CDN 给了坏副本，全都解释不了"1 毫秒内拿到 0 字节、状态码 0"。
浏览器记下的状态码 0 只有一个来源：**这次请求在发出前就被取消了**。
而同一时刻、同一个页面、同一个 UA，用它自己的 `fetch` 去取同一只脚本，拿回来的是 200 和
一个哈希完全正确的字节流 —— 所以挡的不是那个地址，是"让页面去发这个 `<script>` 请求"这件事。
样式表（`<link rel=stylesheet>`）是同一回事：它也没加载起来，所以只放行脚本的话，
看到的是"界面出来了、一个样式都没有"。

**最后一个按钮「自己验一遍后放行（试一次）」**：官网那两只脚本是「跨域 + `crossorigin` +
`integrity`」，浏览器要先过一道 CORS 校验才肯执行它们，没过就只回一句"拒绝"，什么都不说。
这个按钮分两级试，都不会跳过校验：

**第一级 —— 在页面里自己验、自己注（现在走内联，不走 `<script src>`）。**

1. 把两只脚本的字节 `fetch` 回来（**用 `cache: 'no-store'`**）、自己算 `sha384`，跟 HTML 里写的
   **逐字比对** —— 有一只对不上就整体放弃，**一个字都不注入**（这才是真的降级，宁可继续报错）；
2. 把 body 还原成 `_sriCk` 动手之前的样子 —— 官网那张错误图是 `document.body.replaceChildren()`
   换掉的，连 `<div id="root">` 一起没了（官网的 body 里就只有它一个节点）；
3. **把验过的脚本本体塞进 `el.textContent`，以内联方式注进去** —— 不再是 `<script src>`。
4. 样式（`<link rel=stylesheet>`）同样 `fetch` 回文本、插成 `<style>`，而且**排在脚本前面**。

第 3 条是实测逼出来的，也是这一版最要紧的一处。原先插的 `<script src>` 和官网原来那两只一样，
请求在 2 毫秒内被挡掉（HTTP 0、0 字节）。**被挡的是"这个页面去发起一次子资源请求"这件事，
而不是那个地址** —— 同一个页面自己发 `fetch` 拿得到 200 和正确字节（诊断里那两遍重取就是证据）。
所以绕开的办法不是换谁来发请求，是**别请求**：`fetch` 拿到文本、自己验完，内联注进去。
内联脚本不发任何请求，也就没有被挡这回事。样式同理 —— 只放脚本的结果实测是
「界面出来了、一个样式都没有」，因为 `<link>` 也是元素请求。
顺带一个好处：内联脚本按 `appendChild` 的次序当场同步执行，比原来的
`async = false`（动态插 `<script src>` 时得靠它防乱序）更靠得住。
（内联脚本唯一的软肋是页面若哪天上了 `script-src` 之类的 CSP 会被拦 —— 那条路有
`拦截 :` 那行盯着，而且真被拦了第一级会判失败、自动落到第二级。）

**第二级 —— 第一级没成就自动改由父窗（Node 侧）去取、验完再灌进来。** `js/repair.js`
用 Node 的 `https` 把脚本和样式取回来（这一层没有 CORS，也不经过页面策略），
**脚本仍旧按 HTML 里写的那串 hash 逐只验过**，验过了才用 `webContents.executeJavaScript`
灌进页面（样式走 `insertCSS`，没有就退到页内插一只 `<style>`），
最后回读 `#root` 的子节点数，确认官网界面真的挂上来了才算成功。
两级用的是同一把尺子：要么字节和官网上写的一模一样，要么一个字符都不放行。

**样式这边的尺子要短一截，得说清楚**：官网那只 `<link>` 上**没有 `integrity`**
（它的两只脚本有），所以样式**没有哈希可验**。退一档的办法是**只认来源**：
地址必须是 `https` + `*.deepseek.com`，别的一概不注入；取不到就整体收手，
宁可"一样都不做"也不给一个没样式的半成品。（CSS 执行不了 JS，但能用 `url()` 往外发请求，
所以"来源可信"这条线还是得守住。）


按钮上的字会告诉你走到哪一步了（`正在核对哈希…` → `页面侧重插没成，改由父窗取…` → 结果写在
报告里那条蓝色横条上）。父窗那条路可能会不吭声（窗口关掉了、IPC 断了），所以它等 15 秒没回音就
把按钮放回可点状态，不会让你对着一个永远禁用的按钮。

这条路有一个我事先说不准的地方：官网那只 bundle 是在页面刚解析时跑的，
要是它内部依赖"在 `DOMContentLoaded`（或更早）之前初始化"这前提，那么在页面早就加载完之后
再把它灌进去，它可能跑完却不渲染。真遇到就是"报告里那条横条说脚本灌进去了、
但 `界面 : #root 有 0 个子节点`"—— 所以父窗那边不把"没报错"当成功，
一律以 `#root` 里有没有东西为准。

它做成人点的按钮、不自动动手，因为这一步的代价是明确的：**这只脚本不再由浏览器的 SRI 把关，
改由这段代码把关**。校验并没有被跳过 —— 只是从"浏览器验"换成"我们验完再交给浏览器执行"。

报告框里带三个按钮：**重新加载（绕过缓存）**、**在系统浏览器打开**、**复制这些信息**。
它只是往页面上叠一层自己的 div（`data-deepseek-helper="diag"`），不覆盖官网那张错误图，
所以官网的「重新加载」按钮照样能点；重复生成会先撤掉上一份，不会叠成一层层。
这段代码本身也不 `require` 任何东西、全程 try/catch —— 它跑在别人家的页面上，不能连累那个页面。
（`js/repair.js` 是另一回事：它在父窗里跑，那边是插件自己的 Node 环境。）

**放行成功之后，报告不会消失，会收成左上角一条细横条**：`DeepSeek 助手：已放行 ✓ · 失败请求 N`，
后面跟着三个小按钮 —— 「详情」把整份报告重新拉出来（并**重取**一遍，所以看到的是此刻的状态）、
「复制」把最新的一份复制走、「收掉」才是真的撤掉。留这一条是因为**放行只是第一步**：界面起来了，
接下来要登录、要验证码、要拉会话，那些请求要是也被挡，官网只会回一句「网络异常，请检查你的网络状况」——
没地址、没状态码，什么都不说。而这条横条上的「失败请求 N」是活的，复制出来的那份会把
`── 这个窗口里失败的请求` 那一段现拼进去。

**但这条横条本身靠不住 —— 实测撞上过：** 进了登录页、点登录，那一下很可能触发一次页面导航，
报告框挂在官网的 DOM 上，导航就把整个文档换掉了，"左上角横条"跟着消失，回头想复制什么都找不到。
**而且界面上那几条取证路径一个比一个脆**：横条挂在官网 DOM 上（导航即没）、面板按钮要先重新
打包才存在、开发者工具在 uTools 的窗口上不一定打得开。所以要抓的那件事**不该要求用户在界面上
做任何配合** —— 照着复现一次就够了。

### 排查日志：记在一个文件里，不看界面

`js/trace.js` 把关键事件追加写到：

```
%TEMP%\deepseek-hovering-net.log        （即 %LOCALAPPDATA%\Temp\deepseek-hovering-net.log）
```

（路径来自 `utools.getPath('temp')`，拿不到就退到 `%TEMP%` / `%TMP%`；超过 512 KB 会从头来过，
只留最近一段 —— 排查要的是"刚刚那一次"，不是考古。）

里面长这样：

```
[21:03:11.204] === 插件进程开始（站点 https://chat.deepseek.com/） ===
[21:03:14.771] 页面侧认出官网的「资源加载异常」页: https://chat.deepseek.com/（这次是第一次）
[21:03:15.902] 入口脚本没加载成: https://chat.deepseek.com/ → 绕过缓存重载一次
[21:03:22.318] 页面侧认出官网的「资源加载异常」页: https://chat.deepseek.com/（这次是第二次）
[21:03:26.055] 页面侧放行: ok / 已放行
[21:03:41.662] 导航: https://chat.deepseek.com/a/chat/s/...        ← 登录那一下换过文档，这行就证实了
[21:03:48.207] 请求失败: POST https://chat.deepseek.com/api/v0/users/login → 失败（连接层面没成）：net::ERR_FAILED
```

那行 `请求失败` 就是要等的子弹。**`失败（连接层面没成）`（status 0）说明请求根本没发出去 ——
和那两只脚本同一个病；`HTTP 4xx / 5xx` 说明请求走通了、是 DeepSeek 服务端不受理。**

**实测第一次抓到的那颗子弹（2026-10-14，装好的插件里）：**

```
[16:14:11.929] 导航: https://chat.deepseek.com/sign_in
[16:14:14.397] 页面侧放行: ok / 已放行 / （页面结构已还原，样式 1 份）
[16:14:27.890] 请求失败: POST /api/v0/users/login → HTTP 422
[16:14:35.822] 请求失败: POST /api/v0/users/login → HTTP 422
```

读法：**界面这一侧是好的**（放行成功、样式也补上了、登录页正常渲染），
**登录请求也发出去了**（拿到了一个真实的 HTTP 状态码，而不是 status 0），
**是 DeepSeek 的服务器回了个 `422` 把这次请求判掉了**。所以「网络异常，请检查你的网络状况」
是官网把服务端的拒绝翻译成的一句通用话，跟网络没关系、跟"这个窗口发不出请求"也没关系。
422 是"服务端语义层不受理"，它下面还有两种可能 —— 环境/风控不受理，或者这次请求缺了什么 ——
分开它们要靠服务端自己的错误说明，也就是上面那条 `服务端说:`。

**第二颗子弹（同一天，重新打包后再复现一次）：答案在这儿。**

```
[16:26:21.095] 请求失败: POST /api/v0/users/login → HTTP 422 / 我们发的字段: object / 服务端说: {"detail":[{"loc":"body.device_id"}]}
```

服务端把话说清楚了：**这次请求的 body 里少 `device_id`**。这不是风控、不是"官网不欢迎这个窗口"，
是一个具体的、指名道姓的字段没带上。顺藤摸下去（下载官网自己的两份 bundle 翻出来的，
`default-vendors.3473f64207.js` / `main.cc42a0a85c.js`，都是官网公开的静态资源）：

1. 密码登录那个函数里写的是 `device_id: e.deviceId` —— 而 `deviceId` 为 `undefined` 时，
   `JSON.stringify` 会**把这个键整个省掉**（同一个函数里 `mobile` / `area_code` 都被
   `er()` 强制成字符串，偏偏 `device_id` 没有），于是服务端看到的就是"缺这个字段"。
2. `deviceId` 从哪来：官网会往 head 里插一只 `<script data-fp src="/static/fp.min.js">` ——
   那是**数美（ShuMei）的设备指纹 SDK**（`window.SMSdk`），`deviceId` 就是
   `window.SMSdk.getDeviceId()`。官网自己的代码里有 5 秒超时，拿不到就记一条
   `数美设备识别 deviceId 不可用` 然后返回 `null`。
3. 这只脚本**不是 HTML 里写死的**，是运行时由 JS 插进来的 —— 而"元素发起的请求"
   恰好就是这个窗口里被拦掉的那一类（实测：HTML 里那两只脚本和那只样式表都是 0 字节、
   几毫秒结束，而页面自己发的 `fetch` 拿到 200）。

于是整条链子对上了：**指纹脚本没加载成 → `deviceId` 是 undefined → 登录请求里没有 `device_id`
→ 服务端回 422 → 官网翻译成「网络异常」**。和"脚本被拦、页面变资源加载异常"是同一个病根，
只是这次它长在了登录接口上。

所以这一段新加了两样东西去把它钉死（都不是猜的，是要测的）：

- **元素发起的请求没加载成的，单记一行**（`<script>` / `<link>` / `<img>` 的 error 事件，
  捕获阶段才收得到）。这一类和上面 XHR/fetch 那类是两种病：上面是"请求发出去了服务端不收"，
  这里是"请求压根没发出去"。指纹那一只还会额外标出来。
- **失败请求那一行带上"指纹当时的状态"**（`window.SMSdk` 在不在、`<script data-fp>` 插了没有、
  `getDeviceId()` 读出来多长）。deviceId 只报长度和开头几个字符 —— 那是个能用来追踪设备的
  标识，整串没必要落进日志。

**第三层视角：从父窗盯整个网络和控制台（`js/windows.js` 的 `watchChatNetwork` / `watchChatConsole`）。**
页面里那套看得见"谁失败了"，看不见"**是谁拦的**"。所以父窗这边挂了三条路，按"先试哪条"
排好：`session.webRequest` → `webContents.debugger`（CDP）→ `webContents` 的 `console-message`。
前两条给的是 Electron 自己或 CDP 的错误码（`net::ERR_BLOCKED_BY_CLIENT`、
`blockedReason=csp` 这种名字往往直接把拦人的那一层点出来）；第三条是冲着**唯一一句
能直接说清楚的话**去的：

> `Failed to load resource: net::ERR_BLOCKED_BY_CLIENT`

这句话是**浏览器自己**在资源加载失败时写进控制台的。关键在于：它**不经过页面里的
`console` 对象** —— 是浏览器内部直接塞进控制台存储的，所以在页面里包 `console.error`
也收不到它，只有从 `webContents` 这一侧听得见。日志里长这样：

```
[16:26:04.900] 网络层观察已挂上: session.webRequest（这一行只在进程里第一次开对话窗时出现一次）
[16:26:05.100] 网络层出错: GET https://fe-static.deepseek.com/chat/static/main.cc42a0a85c.js → net::ERR_BLOCKED_BY_CLIENT（script）
[16:44:31.093] 网络层观察: webContents 上没有 session，改用 CDP
[16:44:31.094] 网络层观察: 也没有 webContents.debugger，这一层这次看不成
[16:44:31.328] 控制台观察已挂上: webContents console-message（"Failed to load resource: net::ERR_…" 这类行会落到这里）
[16:44:35.001] 页面控制台: Failed to load resource: net::ERR_BLOCKED_BY_CLIENT
[16:26:21.095] 网络层拒绝: POST https://chat.deepseek.com/api/v0/users/login → HTTP 422（xhr）
```

那两行"没成"不是废话，是这个环境交出来的实测答案：**uTools 给的窗口对象是个代理，
不是原生 `BrowserWindow`**（它上面既没有 `session` 也没有 `debugger`，所以前两条路走不通），
而 `console-message` 那条能不能挂上，日志里会有明确一行 —— **挂不上也要留原因，
不静默**（头一版就是失败时只打 `console`，结果日志里看不出到底挂没挂上，白跑一轮）。

只记两种：**出错的**（`onErrorOccurred` / `loadingFailed` / 带 `net::ERR_` 的控制台行）
和 **HTTP ≥ 400 的**（`onCompleted`）。200 的一条都不记 —— 一次页面加载就有几十条，
记了就把有用的淹了。官网自己往控制台打的日常日志（埋点、调试）也一并滤掉，
只留认得出是"没加载成"的那类，并且有上限。过滤器把范围收在 `*://*.deepseek.com/*` 上，
因为 `webRequest` 挂的是**整个 session**，不设范围的话 uTools 自己和别的插件的请求也会跟着进来。
session 是所有窗口共用的，所以网络那层只挂一次（挂两次每条请求会被记两遍）；
控制台那层是按 `webContents` 算的，每开一个对话窗挂一次。CDP 那条有个必须写明的代价：
**它和开发者工具互斥**（同一个 `webContents` 上只允许一个调试器），所以要求"先把开发者工具关掉"。

**第四层：页面里自己动手试（`page/chat-preload.js` 的 `runProbe`）。**
上面几层回答的是"浏览器说为什么失败"，这一层回答的是**"换一种发法能不能成"** ——
而后者才是决定"还有没有路"的那件事。做法很直白：拿**同一个地址**换几种发法各试一次，
成与不成摆在一起：

```
── 探针：同一个地址，换几种发法各试一次
   — / 上的探针（01:55:16）—
   ③ <script src=data:…> : 加载成功
   ② <script src=同源真实地址> : 没加载成（error）（耗时 1ms，HTTP 0）
   ④ <script src=blob:…> : 加载成功
   ⑥ <script src=跨域真实脚本> : 没加载成（error）（耗时 1ms，HTTP 0）
   ⑤ <img src=官网图标（跨域、非脚本）> : 加载成功（耗时 136ms，HTTP 0）
   ① fetch 取同源真实地址 : HTTP 200 / 343703 字节 / application/javascript / 148ms
   ⑦ fetch 取跨域脚本地址（成＝跨域改道可行） : HTTP 200 / … 字节 / …  ← 跨域那条路量这一行
```

（顺序就是完成顺序，所以上面看着是乱的 —— 这正是"谁先回来"的原始样子。）

它为什么值得单独一层：**①②⑥ 这三行的组合，直接把病因锁进"元素发起的请求"这一格** ——
同一个地址，`fetch` 拿得到 200 和 343703 个真字节，做成 `<script>` 就 0 字节、0–1ms 结束；
而 ③④ 说明元素这条机制本身是通的（`data:` / `blob:` 的 script 能加载），⑤ 说明非脚本元素
也没问题。四行合起来，能让"服务端不收我们"和"我们的窗口不让我们这么发"彻底分开 ——
前者没得救，后者**有路可走**，而这两条路走哪条，是这一轮排查唯一真正要问的问题。

⑦ 是后补的一行，理由很具体：跨域那条路能不能走**不由元素决定，由 CORS 决定**（元素被挡是
另一回事），所以得单独量一次跨域的 `fetch`。它成，跨域改道就成 —— 这一条直接决定了官网那些
跨域脚本（包括登录最后那步的验证码）还有没有救。

而且这一版探针把"哪条路能走"也一并量出来了：**①说明字节拿得到、④说明 blob 能当脚本跑**，
两件事叠起来就是一条现成的路（见下面「换个走法」那一节）。⑤ 那行的 `HTTP 0` 是个提醒：
`PerformanceResourceTiming.responseStatus` 对**跨域**资源一律读成 0（那次 `<img>` 明明成了、
耗时 158ms），所以"HTTP 0"本身不是结论 —— 要连同字节数一起看。

跟它一起上的还有 **Reporting API**（`ReportingObserver`，`buffered: true`）。
浏览器会主动上报两类"被拦下来"的事，而且说得比 `error` 事件清楚：`integrity-violation`
（SRI 没过 —— 只有在**真拿到字节**之后才可能出现）和 `csp-violation`（哪条指令、拦的是谁）。
这两条都是浏览器自己下的判断，比从现象上猜可靠。所以"**一条都没报**"本身就是个结论：
不是在 SRI 那一步被挡的，也不是 CSP 挡的。

探针只在**这次真的出现过"没加载成"**的时候跑（登录页那种"界面正常、只是个别脚本没加载成"
的情况也覆盖得到），一份文档只跑一次；结论同时进日志文件和 `sessionStorage`
（后者是为了不被一次导航带走 —— 报告框会随文档消失，这个不会）。

**第五层：把被挡的那一步换掉（`page/chat-preload.js` 的 `installShim`）。**
探针把病因锁进"元素不能自己去取 http(s) 地址"之后，要问的就不再是"谁挡的"，而是
"**这一步不做行不行**"。行 —— 自己把文本取回来，包成 `blob:` 地址，再挂上去：

```
官方那只：<script src="https://chat.deepseek.com/static/fp.min.js">   ← 元素发，被挡
换走法后：fetch 同一地址 → 343703 字节 → Blob → blob:… → <script src="blob:…">  ← 元素发，通
```

口子开在 `appendChild` / `insertBefore` 上（挑它们是因为官网注入脚本就一句
`document.head.appendChild(e)`，源码实测如此）。命中的元素**先不插进文档**：
取文本 → 改成 blob 地址 → 才插。日志里会落两行，成不成一眼可见：
`元素换走 blob: /static/fp.min.js / 343703 字节`。

**实测结果（第一次装上去跑）**：手指纹那只当场就通了 ——
`元素换走 blob: /static/fp.min.js / 343703 字节`，紧接着报告里那行从
「没有 `window.SMSdk`」变成了 **`deviceId 长度 89，开头 BfRfVd（页面插了 <script data-fp>）`**，
登录不再回 422。也就是说：**device_id 这条链，从"指纹脚本加载不成"到"登录成功"整条打通了。**

边界（这几条是**代码里钉住的**，`tools/check.js` 有断言，不只是写在文档里）：

| 边界 | 为什么 |
| --- | --- |
| 同源、跨域都做，但**能不能成由 `fetch` 说了算** | 跨域要 CORS 放行才读得到字节。实测数美的风控云 `castatic.fengkongcloud.cn/.../smcp.min.js` 回 `access-control-allow-origin: *`；回不了的（没这个头、或只回固定源）`fetch` 直接抛错，那就按原样插回去 —— 退化成今天的样子，不会更差 |
| 只碰 `<script>` 和 `<link rel=stylesheet>` | 别的元素（`<img>` 这类）本来就没被挡（探针⑤） |
| 只认 https | 页面自己是 https，http 子资源本来就会被混合内容规则挡掉；`data:` / `blob:` / `file:` 更不该经我们的手 |
| **先看原始 `src`/`href` 属性**，空的一概不碰 | 见下面那个坑 |
| 带 `integrity` 的不碰 | 那类要过 SRI，blob 里的字节未必按原样对得上（BOM、非 UTF-8、换行都可能差一点），换过去只会把"校验没过"引出来 |
| 核对 `Content-Type` | SPA 兜底会把一张 HTML 当脚本发回来（`/undefined` 就真能回 200 + index.html），拿它当脚本灌进去只会炸 |
| 换不成就在**原样**插回去 | 取不回、造不出 blob、类型不对，都退回今天的行为，最坏不变差 |
| 两层封顶：总数 24 只（保险丝）、**同一地址最多试两回** | 要防的是**转圈**（换失败 → 官网重试 → 又换），不是"量大"。头一版只按总数封 12，而登录页一屏就有 **12** 只被挡的元素 —— 那等于帮到一半就停手。所以门槛改成按地址算，总数只当保险丝 |
| 绕开带 `data-ds-probe` 的元素 | 那是探针自己的，必须走原路——不然量到的是被换过的那条路，结论就废了 |
| 不碰 UA / `navigator` / 指纹 | 这一步只换"走哪条路"，不动"我们是谁"——伪身份是另一件事 |

顺序那点值得单独记一笔：一只是"启动过又失败"的脚本元素**不会再加载**（插进文档之后再改
`src` 也不来），而官网那段代码是**先 `appendChild`、后写 `onload`**——所以必须趁元素还在手上
时改地址，把插入推迟到自己取完文本。这样它的 `onload` 才稳稳落在加载之前，不会空等到超时。

**头一版踩的坑（报告里看出来的）**：那版只认"同源"，判据是 `new URL(el.src, location.href)`。
而 `el.src` 是**空字符串**时它会解析成**当前页面地址** —— 于是判成同源，把官网插的
**内联 `<script>`** 也劫走了。报告里那两行就是它：

```
元素换走 blob: /undefined / 8301 字节      ← 8301 字节正是 index.html 自己
```

（`undefined` 是 `node.src || node.href` 两个都空时落到 `fetch(undefined)` 的结果。）
而给 `<script>` 设 `src` 会让它原有的**内联代码作废** —— 那段代码再也不会跑。
现在第一道闸门就是看**原始属性**：`src` / `href` 没有、或者不像个地址（不是 `/…` 也不是
`http(s)://…`），一概不碰。

**这一条是自动的，不走那个按钮**——和「自己验一遍后放行」不是一回事：那个按钮之所以要你点，
是因为父窗那条路得由我们替脚本的完整性背书；这里没有任何背书，字节就是同一个地址、同一个源、
浏览器本来会取的那一份。要不要真在这个窗口里登录，判断仍然在你（见下面「使用环境异常」那段）。

**日志的边界**：只记**地址、方法、结果**这类元信息，不碰请求体、响应体、令牌、验证码 ——
记的是"哪条路没走通"，不是"路上运了什么"。写文件也全程 try/catch：磁盘满、目录只读、
权限不够都只是"少记一条"，不会连累插件本身（`tools/check.js` 里有一条专门测这个）。

**一句自我纠正：那张「页面资源加载异常」的图，不是 SRI 的证据。** 早先我照着报告里
"官网脚本带 integrity"这句话，把它读成了"完整性校验没过" —— 把官网的 HTML 拿下来一看，
事情不是那样。那张图**就写在 HTML 里**，由一个叫 `_sriCk` 的兜底函数渲染：

```html
<script crossorigin defer integrity="sha384-b7GITnoyIfXg73u+…" onerror="_sriCk(this)"
        src="https://fe-static.deepseek.com/chat/static/default-vendors.3473f64207.js">
```

`_sriCk` 干的事是 `document.body.replaceChildren(div)`，把 body 整个换成那张图
（所以报告里那条 `界面: #root 不存在` 不是"没跑到"，是**被替换掉了**）。
函数名里带 "Sri" 是作者的预期 —— 他们大概觉得最常见的病因是完整性校验 ——
但 **`onerror` 对"请求压根没发出去"一样会响**。所以这张图的含义只有一句：
**有只脚本没加载成**，至于是哪种没成，它不说。

而且那只样式表**根本没有 integrity 属性**（HTML 里那行只有 `href` 和 `rel`），
它也一样没加载成 —— 光靠 SRI 解释不了全部。更省事的说法是：**这一整类"元素发起的请求"
在这个窗口里都没成**（实测这批：官网的两只入口脚本、CSS、webpack 懒加载块、
katex、TDesign 那些块、`/static/fp.min.js`、数美的风控云 `smcp.min.js`、
微信登录 `wxLogin.js`、Apple 登录 `appleid.auth.js`、火山引擎的埋点 SDK）。

同一批里还有一只**更干净的证据**：`/static/fp.min.js` 是官网运行时自己插的一只
**同源、无 integrity、无 crossorigin** 的普通 `<script>` —— 它也没加载成。
同源排掉了 CORS 和 CORP，无 integrity 排掉了 SRI，实测耗时 2–3ms 排掉了"网络来回"
（一次真实往返不可能这么快，说明请求**根本没发出去**）。顺带说一句边界：
**`<img>` 这一类现在是被明确测过的**（见上面的探针第⑤行），和 script / stylesheet 不是一回事。

**"是谁拦的"，我已经排除掉了一个最像的嫌疑人**：把 uTools 的 `app.asar` 翻了一遍 ——
`onBeforeRequest` / `resourceTypes` / `loadExtension` / `adblock` 全是 **0 次命中**，
`webRequest` 那 20 来处全部属于一个不相关的 JS 服务端框架（在那儿只是个形参名）——
**uTools 没有在拦请求**。倒是翻出两件有用的事：uTools 给插件的内置浏览器用的是
**每个插件一个的独立 session**（`persist:utools.plugin.<插件id>.ubrowser`），
而且它给插件的是一个**窗口代理**，不是原生 `BrowserWindow`（所以 `session` / `debugger`
都取不到 —— 这也是上面两条网络观察路走不通的原因）。所以这个"到底是谁"只能问浏览器自己要，
也就是上面那几层里的错误码。

**一处例外，是为了 422 这类状态码开的**：`status 0` 一眼就知道是"请求没发出去"，
而 `422` / `403` 是"发出去了、服务端不收"—— 不收的理由只有服务端自己知道，
官网的界面只会把它翻成一句"网络异常"。所以**失败的响应体会截 400 字留下**：

```
[16:14:27.890] 请求失败: POST /api/v0/users/login → HTTP 422 / 我们发的字段: {email:str(0) code:str(6) ...} / 服务端说: {"code":...,"msg":"..."}
```

同一行里还记下**我们这次发出去的字段名** —— 422 另一种常见病因是"缺字段"，
看字段名就能对上号。但**只有名字和值的长短，没有值**：`{email:str(0) code:str(6)}` 说的是
"email 这个字段发了，但是空的；code 发了，6 个字符"。手机号、邮箱、验证码本身**不进日志**，
因为这份日志是会被贴来贴去的。认不出来的请求体（Blob、流）只报个类型就退开 —— 猜比不报更坏事。

边界仍然守着：**只读失败的、只留 400 字**；正常请求的响应体（包括登录成功后的令牌、
对话内容）一个字都不读 —— 那才是不该碰的部分。请求体同理：**只在失败时取字段名**，
值一个字不记。

**两条不依赖页面 DOM 的界面入口**，都在**主面板**（搜 `deepseek` 进来的那一页，往下滚到最下面
那张「排查」卡片）：

| 入口 | 干什么 |
| --- | --- |
| **打开对话窗开发者工具** | `webContents.openDevTools({ mode: 'detach' })`。**这是排查请求问题最直接的工具** —— Network 面板会给出每条请求的完整因果（谁发起的、有没有发出去、卡在哪一步），比我们自己在页面里包一圈强得多。拆成独立窗口是因为对话窗默认只有 460 宽，DevTools 停靠进去页面就没法看了 |
| **复制失败请求记录** | 父窗 `executeJavaScript` 去问页面要 `window.__dsHelper.netReport()`，取回来在**父窗**写剪贴板。页面那边在不在都无所谓 —— 接口是每个新文档都会重新挂上的 |
| **复制排查日志** | 把 `%TEMP%\deepseek-hovering-net.log` 的尾巴读出来写剪贴板（`js/trace.js` 的 `read()`，默认最后 32 KB、从整行开头切）。**这条是唯一能看到浏览器自己那句 `Failed to load resource: net::ERR_…` 的入口** —— 那句话直接点名是谁把请求掐掉的，而它只在父窗那一侧，页面上的报告看不到 |

**DevTools 的另外两个等价入口**（代码那条路万一走不通）：uTools 给插件窗口挂了右键菜单，
里面有一项就是**「开发者工具」**。这一条不是猜的：uTools 的 `app.asar` 里能搜到 i18n key
`menu.plugin.devTools`（中文标签就是"开发者工具"，和 `menu.plugin.detachPlugin`、
`menu.plugin.pluginManagement` 挨在一起，是插件窗口的右键菜单），`openDevTools` /
`closeDevTools` / `isDevToolsOpened` 也在它的窗口快捷键处理里。另外 `app.asar` 里搜不到任何
`devTools: false`，说明它没有把插件窗口的 DevTools 关掉。

**但 `Ctrl+Shift+I` 这条要打个问号，实测按了没反应。** 在 asar 里，那一串 `Ctrl+Shift+I`
是**菜单项上显示的 accelerator**，而 Electron 里这种只写在菜单模板里的 accelerator
**不注册成系统或窗口级快捷键**（菜单没弹出来时它不生效）。真正处理按键的那段代码里对应的是
`alt` + `KeyI`（`isDevToolsOpened` → `closeDevTools` / `openDevTools({mode: 'undocked'|'bottom'})`），
所以**更可能是 `Alt+I`**。这条我只能在 GUI 里试，两种都值得按一下；按不动就走右键菜单。

**失败记录为了跨导航活下来，落到了 sessionStorage**（键 `deepseek:netLog`，同源、同窗口，
关窗即弃）。新文档起来时读回来，所以就算中间被导航打断，记录还在。这一段里还多包了一个
**WebSocket**：官网的实时通道就是它，连不上时页面同样只会说"网络异常"。包构造函数比包 `fetch`
代价大，所以只在**实例上**挂 `error` / `close` 两个监听、原对象原样返回（`new` 里返回对象就是它，
`instanceof WebSocket` 仍然成立），`prototype` 和四个常量都指回/照抄原生的。
（`close` 里 `wasClean` 为真的正常关闭不记 —— 那不是故障。）

**遇到登录失败时，按这个顺序看**：先看上面那个日志文件的最后几行（最省事，什么都不用点）；
日志里没有 `请求失败` 就再去开 DevTools 的 Network 面板（能看到更细的因果：
Initiator、Timing、是不是 CORS 预检挂的）；两条都没有再说。

**已经实测排掉的几条**（2026-10-14，在装好的插件里跑出来的报告）：

| 阵营 | 证据 |
| --- | --- |
| CDN 给了坏副本 | 排掉。两只脚本各取两遍（绕过缓存 / 走缓存），四个哈希都和 HTML 里的 `integrity` 一模一样 |
| 本地缓存里躺着坏副本 | 排掉。走缓存那次取回来也是对的（且响应带 `vary: Origin`，缓存按 `Origin` 分桶） |
| 被改了 UA 特征拦了 | 排掉。窗口里的 UA 是 `uTools/8.0.0 Chrome/132.0.6834.210 Electron/34.5.8`，而**同一个页面、同一个 UA、同一个会话里**发出去的 `fetch` 拿到了 200 和正确字节 —— 拦 UA 的话那次也该拦 |
| 代理 / 加速器换了内容 | 排掉。同一台机器上 curl 带 `Origin: https://chat.deepseek.com` 取回来的响应里，`access-control-allow-origin` 正确回显、`content-type: text/javascript`、字节哈希与 `integrity` 一致 |
| 页面 CSP / COEP 之类 | 排掉。页面只有 `content-security-policy: frame-ancestors 'none'`，资源响应没有 `cross-origin-resource-policy` |

剩下的可能就两类，**报告里那行 `这次加载` 一锤定音**：
浏览器当时那次请求是**没拿到内容**（被限流 429/403、连接被重置 —— 瞬时问题），
还是**拿到了正确内容却被拒**（CORS/校验层 —— 与网络无关）。

**实测落在后者，而且比"被拒"更极端：那次加载是 `HTTP 0、0 字节、2–3ms`。**
一个请求若真上了网络，再怎么被拒也不会在几毫秒内拿到 0 字节 —— 这个组合只有一个来源：
**它在发出去之前就被取消了**。所以结论是"窗口层面挡掉了这次子资源请求"，不是网络、
不是代理、不是缓存、不是 CDN、也不是 UA。

至于具体是谁挡的，现在能说的是这些：uTools 的 `app.asar` 里 `onBeforeRequest` /
`resourceTypes` / `loadExtension` / `adblock` **一次都没出现**（`webRequest` 那 20 来处
全属于一个不相关的 JS 服务端框架），所以**不是 uTools 在拦**；它给插件的窗口是个
**代理对象**（`session` / `debugger` 都取不到），所以"从父窗挂个钩子看错误码"这条路
在这个环境里多半走不通 —— 日志里会明确写出哪条挂上了、哪条没挂上。
真正把这一格锁死的是页面里那组探针（见上）：**同一个地址 `fetch` 拿得到 200、
做成 `<script>` 就 0 字节结束**，而 `data:` / `blob:` 的 script 与非脚本元素都是通的。
这两件事合起来说的不是"网络不通"，而是"**这个窗口不让页面用元素的方式去发子资源请求**"。

好消息是**修法不依赖查出是谁**：既然"让页面去发这个请求"这一步过不去，就不发它了。
两批资源、两条不同的路，分工是清楚的：

| 哪一批 | 走哪条路 | 为什么是这条 |
| --- | --- | --- |
| HTML 里那两只**入口脚本**（带 `integrity`） | 报告里第一个按钮 → 父窗那条路：Node 侧取回 + 按 `integrity` 验哈希 + `executeJavaScript` 灌进页面 | 它们写在 HTML 里、带着哈希，得**先验后灌**；而且它们不是元素插入的，改道那层够不着 |
| 官网**运行时**插的那几只（`/static/fp.min.js` 等，无 `integrity`） | 第五层那个**元素改道**，自动 | 它们不在 HTML 清单里、没有哈希可验，是**元素自己发的请求**——正是被挡的那一类，也正是探针③④先探过的路 |

两条路都不是"绕过服务端的拒绝"：服务端给的是 200（①实测），被挡的是"元素直接去取"这个动作。

**放行之后还有一步：登录。这一问已经有答案了（见上面两颗子弹）。**
界面这一侧没有问题（实测：登录页正常显示、样式齐全、脚本全部执行）。
当初列了三种可能，现在两条被证据排掉、一条被证据钉住：

| 可能 | 是"怎么一回事" | 现在怎么看 |
| --- | --- | --- |
| 本机那个"挡子资源请求"的东西把官网的登录接口也挡了 | 我们自己的窗口问题 | **排掉了**：那种病是 `status 0`、0 字节；这次拿到了真实的 `422`，请求发出去了 |
| 这次请求缺了某个服务端要的字段 | 我们这边 —— 而缺的那个东西，正是被同一层挡掉的那只脚本该算的 | **就是它**：服务端指名 `body.device_id`，而 `device_id` 来自官网自己的设备指纹脚本 `/static/fp.min.js`（数美 SMSdk）。这只脚本是运行时插进来的 `<script>`，正落在"元素发起的请求被拦掉"那一类里。**已经修好并实测通过**：元素改道之后，报告里那行从「没有 `window.SMSdk`」变成 `deviceId 长度 89，开头 BfRfVd（页面插了 <script data-fp>）`，登录不再回 422 |
| DeepSeek 服务端不受理这个环境的请求（风控 / 环境不可信） | 官网有意为之 | **不适用**：服务端要说的是"你没给我 device_id"，不是"我不收你"。风控这件事本身仍然存在（官网页面上那条「使用环境异常」提示就是它），但它不是这条 422 的原因 |

第二行是"能修"的那一类，而且修的方向很明确：**让官网自己的指纹脚本在它自己的页面里跑起来**。
要说清楚的是这算什么、不算什么：

- **算**：把官网公开的静态资源取回来、让它在官网自己的页面里正常执行。和放行那两只被 SRI 拦掉的
  脚本是同一件事 —— 我们不伪造任何东西，指纹是它自己的 SDK 在这台机器、这个窗口上算出来的真值。
- **不算**：不伪造 UA / 指纹 / 设备型号去冒充另一个环境，不藏这个窗口是 uTools（官网那条
  「使用环境异常」提示照样会浮出来，我们没有遮它）。**如果哪天服务端说的是"我不受理这个环境"，
  那就不该绕** —— 那条线在这儿。

```
https://a0fea896111e.edge.sdk.awswaf.com/a0fea896111e/3a8b889b892b/challenge.js
```

也就是说，这一步是**AWS WAF 的验证码控件**：官网插两只**跨域** `<script>`，然后调
`AwsWafCaptcha.renderCaptcha(容器, { apiKey, onSuccess })`。两只脚本正落在被挡的那一类里 ——
这就是元素改道现在把**跨域**也一起接手的原因（能不能成看 CDN 给不给 CORS，见上面那张边界表）。

还不知道、也不该猜的两件事：

1. **那两只 awswaf 脚本到底有没有被挡**。用户那份报告是在验证码那一步**之前**取的，
   `── 没加载成的资源` 里没有它们。下一份报告（走到验证码那一步之后再取）会直接说明：
   有它们 + `元素换走 blob（跨域）: …aws…jsapi.js / … 字节` 就是接上了。
2. **AWS 的验证码控件是不是渲染在一个跨域 `<iframe>` 里**。若是，控件内部的脚本就在
   **子文档**里，而我们这一层只跑在主文档（Electron 的 preload 默认不进子框架），
   够不着 —— 那种情况下这一格就修不了，得如实说，不是"再改改就好"。

为什么值得把这条写清楚：**"登录能不能用"和"能不能过图形验证"是两件事。**
前者已经通了（device_id 那条链），后者是风控在最后一道门上给的额外一题。

**还有一条候选，现在看是站不住的**：uTools 的 app.asar 里能搜到 `--disable-web-security`
（和 `--inspect`、`--remote-debugging-port` 列在一起），早先我用它解释过
"开发时好好的、打包安装后才弹这张图"。但它说不通这次的证据：关掉/打开 CORS 检查
**只会让请求成功或失败，不会让请求"0 字节、几毫秒结束"** —— CORS 失败的前提恰恰是
**已经拿到了响应**（错误报告里那行 `这次加载` 就会显示 HTTP 200 加字节数）。
实测是 HTTP 0，所以这一条排除。**"开发时 vs 打包后为什么不一样"这个问题，现在还欠着**
—— 我问下探针的结果正是为了这个：探针跑出来的是"这个窗口现在允许哪种发法"，
它和"两种装载方式走的 session / 窗口实现不同"能不能对上，比对着看才有意义。

**顺带一个自纠**：早先我说"报告里的 `Access-Control-Allow-Origin` 空就是不通过"，
这是错的。那个头**不在** JS 可见的响应头白名单里（只有 `Cache-Control`、`Content-Type`
这几个在内），所以页面里 `headers.get('access-control-allow-origin')` 读不到**不代表服务器没发**。
事实上同页面那次 `fetch` 能把字节读出来，就已经说明 CORS 是过的。报告里这行现在标成"（读不到）"。

**救活之后，官网页面上会浮出一条它自己的提示：「使用环境异常 —— 当前页面的使用环境可能存在
数据和隐私泄露风险，为保障安全，建议您使用我们的官方产品。」** 那是 DeepSeek 自己的检测在说话，
**插件没有遮它、也没有绕它** —— 我们只是把官网本该跑起来的代码放行回它自己的页面，
这条提示是官网的 JS 跑起来之后自己渲染的。它说的也是实话：这是个非官方客户端，
令牌停在 uTools 给这个窗口的内存会话里（见下面「登录态不落盘」）。要不要在这个窗口里登录、
登录之后聊什么，这个判断该你自己下；插件的立场是"把你自己的账号在你熟悉的那个界面上打开"，
不是"藏住这是谁在访问"。这条提示反过来也是一条线索：**官网确实在做环境检测**，
所以"从这个窗口发出去的某些请求被挡掉"为什么偏偏只发生在这个窗口里，也就没那么难理解了。

**关于 uTools 的 UA**（顺手记一笔，值得留着）：本机 uTools 8.0.0 的窗口 UA 并没有把 `Electron/`
抹掉，它是 `…AppleWebKit/537.36 (KHTML, like Gecko) uTools/8.0.0 Chrome/132.0.6834.210
Electron/34.5.8 Safari/537.36`。所以"用 UA 判断是不是真浏览器"的站点（部分 WAF 就吃这一套）
是能看出这个窗口不是普通 Chrome 的 —— 这次不是它的锅（见上表），但以后遇到疑似拦截可以先看这个。

**悬浮球不会永远待在那儿。** uTools 的插件进程只有在被"进入"过之后才存在，而且官方文档写明：

> uTools 主窗口隐藏后，插件应用可能会在用户设定的时间（默认 3 分钟）内自动退出。

悬浮球就活在这个进程里，所以 uTools 主窗口关掉几分钟后，球会跟着消失。几种应对：

- **重新召唤**：再在 uTools 里搜一次 `deepseek` 回车，球就回来了（这条一定有效）。
- **改设置**：uTools 设置里有控制插件退出后台后多久结束运行的选项（本机 uTools 8.0.0 上看到的
  相关文案是「跟随主程序同时启动运行」/「退出到后台立即结束运行」这类开关，各版本措辞可能不同），
  按需调整即可。
- **代码兜底**（本版本没做）：`utools.requestSchedule()` 注册一个定时任务，
  `utools.onScheduleTrigger()` 里调 `windows.ensureBall()`。官方文档明确该事件在插件未运行时
  也会拉起插件进程。`ensureBall()` 已经做成幂等的，接上去就能用。

**登录态不落盘：重启 uTools 会掉登录，需要重新登一次。**

`createBrowserWindow` 建出来的窗口用的是 uTools 给它的会话，**不是持久化会话**，
浏览数据（Cookie、localStorage —— 也就是官网的登录令牌）只待在内存里。
在本机 uTools 8.0.0 上把 `%APPDATA%\uTools` 翻了一遍，找不到任何落盘痕迹：

| 查了什么 | 结果 |
| --- | --- |
| `Partitions\` 下有没有这个插件的会话目录 | 没有。只有 uTools 自己的 `utools.app` 和 uBrowser 那一个（持久化会话一定会在 `Partitions\` 下留一个目录） |
| 两个 Cookie 库（默认会话的 `Network\Cookies` 和 `utools.app` 分区的同名文件） | 都停在上次改动时间，里面没有任何 `chat.deepseek.com` 的条目 |
| 默认会话的 `Local Storage\leveldb` | 写日志是 0 字节 —— 从来没写过；`utools.app` 分区那份里只有 `file://` 开头的 uTools 自家页面 |
| 整个 `%APPDATA%\uTools` 里搜 `deepseek` 字样（ASCII 和 UTF-16 各搜一遍） | 只搜到插件自己的 dbStorage（`deepseek:lastChatUrl` 这些键） |

所以边界是**进程**，不是窗口：

- 关掉对话窗再打开、插件退到后台（`onPluginOut(false)`）、改设置 —— 登录态都在，不用重登；
- **完全退出 uTools 再启动 —— 要重新登录**，页面缓存也是冷的。

30 秒验证（这一步得你在 GUI 里跑，上面那张表是我在没有 GUI 的情况下能拿到的最硬证据）：
打开对话窗确认已登录 → 从托盘**完全退出** uTools → 重新启动 → 再打开对话窗，看是不是还在。

嫌麻烦的话：改成「在浏览器中打开」（系统浏览器的登录态是持久的）；
或者接受重启后重登一次（官网登录态本身有效期很长，登一次管很久）。
代码上还有两条路可走，都没默认做：一是把官网存进 localStorage 的令牌镜像一份到插件的
dbStorage、开窗时写回去（能做，但等于多存一份你的登录凭证，官网改了存储结构就失效）；
二是给对话窗指定一个持久化 `partition`（见下）。

**为什么没有直接给对话窗换个持久化 `partition`。** 这看着是最直接的解法
（`webPreferences: { partition: 'persist:utools.plugin.deepseek' }`），但有两个坑：
uTools 自己构造 `webPreferences` 时很可能把这个字段覆盖掉，写了也白写；
更要命的是，"记住上次的会话"依赖 uTools 往官网页面上注入 `utools` 全局（见下一条），
而注入是挂在**它自己的那个会话**上的 —— 换个会话可能连这个全局一起丢掉，
那就成了"修好登录、弄坏记住会话"。没有 GUI 可以实测的前提下，不值当赌这个。

**"记住会话"依赖 uTools 往官网页面上注入的 `utools` 全局。** `page/chat-preload.js` 会跟着窗口
一起跑到 `chat.deepseek.com` 上执行，它用来上报地址的 `utools.sendToParent` 在那边能不能拿到，
文档没有承诺。**本机 uTools 8.0.0 实测是能拿到的** —— 插件 dbStorage 里已经躺着两条真实记录下来的
会话地址，说明"在官网页面上把地址报回父窗"这条链路是通的（这条只能靠实测确认，没法从文档推出来）。
万一哪天插件更新后不注入了，会退化成"每次都从首页进"，其余一切照常，控制台里会有一条
`[chat] 这个页面上没有 utools 全局…` 的 warn。想确认的话，在对话窗里 `Ctrl+Shift+I`
打开 DevTools，切到一个会话，看有没有这条 warn。

**悬浮球的透明区域会吃掉一点桌面点击。** 球窗是 60×60 的透明窗口，圆角外的四个角虽然看不见，
但点上去仍然算点它。右键菜单展开时窗口会临时撑大，菜单开着的那几秒透明区域也更大 ——
这与原生菜单的行为一致。

**图标是 DeepSeek 的，不是我们的。** 插件图标和悬浮球用的都是官网 favicon 那只鲸鱼
（见 `assets/whale.svg`），商标权归 DeepSeek。自己用没问题，要往插件市场发布的话，
建议换成不含官方商标的图。

## 实现要点

- **官网是页面自己去打开的**：`createBrowserWindow` 的第一个参数只收插件目录内的本地路径，
  而它返回的窗口实例上**没有 `loadURL`**（类型定义里写着有，实测 uTools 8.0.0 直接抛
  `win.loadURL is not a function`）。所以跳转交给 `page/chat.html` 自己 `location.replace` ——
  顶层导航是浏览器原生行为，不依赖任何 uTools API。
- **对话窗的 preload 跑在别人家网站上**：窗口导航到官网后，`page/chat-preload.js` 会在
  `chat.deepseek.com` 的页面里再执行一遍。所以它不 `require` 任何模块（那里未必还有 Node 环境），
  也从不假设 `utools` 存在，全程 try/catch —— preload 抛异常会连累它所在的那个页面。
  官网是 SPA，切换会话走 `history.pushState`，不发任何事件，所以除了改写
  `pushState/replaceState` 和监听 `load/hashchange/popstate`，还兜了一个 2 秒心跳。
- **点击与拖拽同一颗球**：没有用 `-webkit-app-region: drag`，因为被声明为拖拽区的元素不再派发
  鼠标事件，那样点击就没了。改成 JS 实现：按下后位移超过 4px 才算拖拽，否则算点击。
- **拖拽由悬浮球页面驱动**：uTools 主窗口隐藏后，主进程侧的定时器会被 Chromium 后台节流到约 1Hz，
  而悬浮球窗是可见窗口，不受影响。球页用 `utools.getCursorScreenPoint()` 按帧读取光标位置，
  只把"相对按下点的位移"发给父窗，边界夹取和实际 `setPosition` 都在父窗做。
- **过渡动画放页面里**：透明窗口上调用 `win.setOpacity()` 会破坏图层合成导致整窗不可见，
  所以入场动画一律用 CSS 的 `opacity` / `transform`。
- **`onPluginOut` 里什么都不能销毁**：官方文档警告，在插件自动退出时不要关闭自定义窗口，
  否则会关掉用户正在用的窗口。悬浮球正是靠 `isKill === false` 这条路径活着。
- **IPC 只注册一次**：`ipcRenderer.on` 是进程级的，不随窗口销毁解绑，重复注册会让每条消息
  被处理两遍（球会一次开出两个对话窗）。主 preload 里用 `setupOnce()` 兜住。
- **快捷键只能"借"uTools 的**：插件侧**没有**注册系统级热键的 API。uTools 的做法是让用户在
  它自己的设置里，给 `plugin.json` 里声明的某条**指令**绑键，按下时打开插件并告诉你
  `from === 'hotkey'`。所以插件能做的只有两件事：`utools.getCmdHotKey(指令名)` 读出当前绑了
  什么键显示到面板上，`utools.redirectHotKeySetting(指令名)` 把用户送到设置页 ——
  后者官方文档写明**只负责跳转，不会创建或修改绑定**。面板里没法直接抓按键组合，就是这个原因。
  为这条指令单开了一个 feature（`deepseek-window`）而不是复用主 feature，并且给它加了
  `mainHide: true`（"通过非搜索框入口触发时，不主动显示插件主窗口"）——
  否则每次按快捷键，uTools 搜索框都会先闪一下再被收走。
- **窗口焦点判断要能降级**：判断"窗口在不在眼前"用的是 `win.isFocused()`，这个 API 在 uTools
  各版本的窗口代理上不保证存在（类型定义里没有）。所以做了降级：拿不到就只做"调到前台、
  永不关窗" —— 宁可白按一下，也不能把用户正想看的窗口关掉。`warnOnce` 只提醒一次，不刷屏。
- **官网自己的错误页要认得出来**：官网的脚本带 SRI 校验，没过就把 body 换成"资源加载异常"那张图。
  这种时候 `location.reload()` 是没用的（坏副本还在缓存里），得让父窗走
  `webContents.reloadIgnoringCache`；而这个方法在 uTools 的窗口代理上是否存在同样没保证，
  所以降级链是"绕过缓存重载 → 普通重载 → 页内 1.2 秒后自己 reload"（见 `已知限制` 那一节）。
  再失败一次就不再刷新，改为**在页面里做现场侦察**：同一只脚本取两遍
  （`fetch(src, { cache: 'no-store' })` 和默认缓存模式），各自
  `crypto.subtle.digest('SHA-384')` → base64 → 和 `integrity` 属性比。
  两遍一比就能分开"缓存里那份是坏的"和"链路上一直在换字节"，再叠上
  `Content-Type` 这个响应头，把"网络换了字节"和"拿回来的根本不是 JS"也分开 ——
  浏览器对 SRI 失败不给原因，`fetch` 的 TypeError 对"被拒"和"网络不通"也不区分，
  所以只能自己把这几个量测出来，比让人去翻 DevTools 强。
  （别指望 `Access-Control-Allow-Origin`：它不在 JS 可见的响应头白名单里，读不到。）
- **兜底修复走父窗，不在页面里硬来**：页面侧"自己验完再插 `<script src>`"实测救不回来
  （请求压根发不出去，和官网原来那两只一样），所以失败之后自动改由父窗做：`js/repair.js`
  用 Node 的 `https` 取回两只脚本、`crypto.createHash('sha384')` 和 HTML 里写的 `integrity`
  逐只比过，再用 `webContents.executeJavaScript` 灌进页面；样式一并取回、走 `insertCSS`
  （没有就插 `<style>`），排在脚本前面。最后回读 `#root` 的子节点数确认界面真起来了。
  几个细节值得记：一是**页面侧现在也改成内联注入了**（`el.textContent` 而不是 `el.src`）——
  被挡的是"页面发起子资源请求"这件事，内联脚本不发请求；二是**先全验完再开始注入** ——
  第二只对不上时一个字符都不放行；三是**注入前必须先还原 body** —— 那张错误图把 `#root`
  一起删了（官网 body 里就它一个节点），不还原就没地方可挂；四是**样式的尺子短一截**：
  官网没给 `<link>` 写 `integrity`，所以只能守住"只认 https + `*.deepseek.com`"。
  校验没有被跳过，只是从"浏览器验"换成"我们验完再交出去"。这段流水线的依赖（取字节、
  灌代码）是从调用方注入的，所以 `tools/check.js` 能用假件把成功 / 哈希对不上 / 取不到 /
  样式来源不对 / 界面没起来几条路各跑一遍，不必依赖网络。
- **页面与父窗之间只有两条通道**：页面跑在别人家网站上，不能 `require electron`，
  所以没有 `ipcRenderer`。页面 → 父窗走 `utools.sendToParent`；父窗 → 页面没有对应的 API，
  只能 `executeJavaScript` —— 于是页面把入口挂在 `window.__dsHelper` 上等它来敲
  （`restoreBody` / `showRepairResult`）。结果回传时 `JSON.stringify` 要**走两遍**：
  嵌进 JS 字符串字面量里，少一层就会拼出语法错误的代码，而"页面里什么都没发生"这类故障最难查。
- **失败请求的记录只观察、不改写**：`XMLHttpRequest.prototype.open/send` 和 `window.fetch`
  各包一层，原函数照常调用、返回值原样返回、异常照旧抛出去 —— 那是别人家的页面，
  包一层已经够冒险了，再"顺手"改点什么就越界了。记录上限 60 条（滚动丢弃），
  只留失败的（`status === 0` 或 `>= 400`），报告里列最后 12 条；同时**落一份到
  sessionStorage**，因为登录那一步很可能触发一次导航，页面里那份数组会跟着文档一起没。
  `WebSocket` 只包构造函数、只在实例上挂 `error`/`close`，实例原样返回
  （这样 `instanceof` 和四个常量都还是对的）—— 包构造函数的代价比包 `fetch` 大，
  不到万不得已不做，而官网的实时通道正是 WebSocket，所以做了。
  **报告正文里那一段是每次点「复制」时现拼的**（`reportLines(currentReport)`），
  不是生成报告那一刻的快照 —— 要抓的故障恰恰在报告生成之后。
  **失败那次发出去的字段名也记**（`bodyKeys`），但只说名字和值的长短、不说值：
  422 另一种常见病因是缺字段，看名字能对上号，而值里是手机号、邮箱、验证码 ——
  这份日志是要被贴来贴去的，那些不该出现在里面。
- **排查入口放在父窗，不放页面里**：报告框挂在官网 DOM 上，导航一下就没了（实测撞上过：
  进了登录页、点登录，回头"左上角横条"已经不在）。所以主面板上另有两颗按钮 ——
  「打开对话窗开发者工具」（`webContents.openDevTools({mode:'detach'})`）和
  「复制失败请求记录」（父窗 `executeJavaScript` 问页面要 `netReport()`，取回来在父窗写剪贴板）。
  这两条都不依赖页面上还在不在。拿不到 `openDevTools` 时把 GUI 里的等价入口
